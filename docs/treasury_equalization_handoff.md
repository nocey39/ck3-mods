# 国库统筹财政 0.7.4：故障机 Codex 交接

这份交接供另一台实际发生故障的电脑继续排查。**本次审查所在电脑不是实际故障机；本次修复尚未在 CK3 引擎中推进日期验证。** 不要将源码测试通过、本机存档快照正常，写成故障已经复现或已经彻底解决。

## 版本与问题背景

用户反馈：天朝中央有收入，但部分下级的发展、军事拨款出现问题；此前 Gemini 修改加入了较多限制逻辑，用户要求全面排查、修复明确缺陷，不确定的玩法调整先询问。

本次涉及三个不同版本，不能混用：

| 来源 | 版本 | 含义 |
|---|---|---|
| 本次开始时的 GitHub `main`，提交 `760e6ad` | 0.6.7 | 仓库当时的旧版本，不是审查电脑实际安装版本 |
| 审查电脑原安装目录 | 0.7.3 | 本次修复的实际代码基线，包含尚未同步到上述仓库基线的 0.7.x 改动 |
| 本次提交的源码 | 0.7.4 | 保留 0.7.3 已有机制并修复下述问题；政策缓存版本为 14 |

目标游戏版本为 CK3 1.21.0.3。故障机的游戏、模组和存档版本均须重新确认，不能从本机情况推断。仓库里的 0.7.4 代码相对旧 GitHub 基线也包含原本已存在于 0.7.3 的功能，例如定向征税、私库双通道分流、游戏规则和时代储备曲线；不要把整个 0.6.7→0.7.4 差异都归因于本次修复。

## 用户已经确认的玩法

**富裕文官地方仍保留少量基础发展权重。** 需求系数连续限制在 `[0.15, 2]`，财富扣减最多 50%，因此模组新增的有效发展权重至少为基础需求的 7.5%。这是权重下限，不是固定金额保底：中央没有可用资金、发展份额为 0%、不符合接入资格时，实际发展支付仍可能为零。

军事地方继续按原生军事职责领取军费，不额外领取本模组的发展拨款。不要擅自把军事拨款改成所有封臣均分，或把富裕文官重新改成零权重。需要改变这些规则时先向用户说明影响并询问。

## 已完成的源码修复

1. **预算口径**：`teq_measure_budget` 直接读取原生 `character_treasury_new_budget_capacity`，负值按零处理。停止用月结余加旧计划拨款倒算，消除原生重算、接收人变化与限额造成的旧账错配。总预算为 `E = max(C, 0) × (1 − 中央留存比例)`，C 是扣除非预算经常支出后的原生可用预算；不从存款额外取款。
2. **年度重算保护**：将保护挂钩从错误的 `yearly_playable_pulse` 移到原版实际执行 AI 备用预算的 `random_yearly_playable_pulse`。没有恢复整份原版年度文件覆盖。
3. **AI 月度维护**：取消 AI 结余处于约 -5 至 25 时跳过非季度重算的门槛。合格中央每月维护预算、待遇与地方状态。
4. **地方接入**：新增 `teq_register_region`，在角色作用域重新数直辖郡，在地方主要头衔记录财政归属和权重，向中央名单去重入列，再立即应用地方修正并同步中央。新封臣不再先纳税、停止返款，却等季度才接入拨款；继承接入同样登记、补全名单。
5. **退出、继承与维护**：中央退出时释放其地方状态并恢复原生预算基准；合格继承人继续使用主要头衔上的设置和地方名单。清理旧版“只有征税、没有入列”的状态及中央遗留地方标记；补回缺失的拨款/返款修正。需求汇总、月度维护与退出清理均校验当前财政归属，避免旧名单条目干涉已经转封的地方。
6. **发展基准上限**：在原生预算执行后、改写基准前，以 `容量 × 通道份额 ÷ 原生基准` 采样发展、军事、枢机的实际有效接收单位。发展安全上限使用原生发展接收单位，停止用地方需求总和加天朝固定 0.25 推算；原生部会、契约和其他修正被纳入采样。最终配置支付按各通道单位乘最终基准记录，仅用于诊断，不再参与预算收入倒算。
7. **富裕地方权重**：按用户确认取消储备约达目标 185% 时突然归零的断点，保留连续基础权重。
8. **迁移与说明**：政策版本提升至 14，首次接入重建地方缓存，保留已有私库比例、中央留存比例、发展/军事份额和工资微调；修正公共收入说明与过时 README。已有的 0% 份额也保留，不擅自恢复默认。

实现入口见 [模组说明](../treasury_equalization/README.md)、[核心效果](../treasury_equalization/common/scripted_effects/teq_effects.txt)、[需求与预算值](../treasury_equalization/common/script_values/teq_values.txt)、[资格触发器](../treasury_equalization/common/scripted_triggers/teq_triggers.txt) 和 [事件挂钩](../treasury_equalization/common/on_action/teq_on_actions.txt)。

## 证据边界

- 本机只读检查过原版脚本、引擎导出接口、当前 17 个启用模组和四份已有存档快照；未修改这些存档，未进行引擎日期推进测试。
- 本机四份快照中，天朝发展和军事基准均非零；较新快照可见文官、军事地方及原生部会/大元帅接收人。这不能证明故障机的特定封臣已经收到拨款，也没有复现用户描述的间歇断款。**四份快照不代表故障机。**
- 本机 12 个原生 effect、5 个事件剥离 TEQ 注入后与原版一致；5 个契约保留原生回退税率和征召兵行为。该模组组合未发现相同预算定义、窗口或额外重算冲突，故障机必须重新扫描自己的加载列表。
- 静态及源契约检查 8/8、财务源码回归 5/5 通过；同一组工具对原样 0.7.3 分别为 4/8、1/5。它们检查或执行有关源表达式，**不是 CK3 引擎模拟器**，不能验证引擎缓存、实际接收人和多人同步。

以下尚待验证：故障机复现、修复版旧档完整迁移、连续月度实际收支、间歇断款原因、长局性能与多人联机。原始日志、存档和本机安装脚本不应上传仓库。

## 故障机继续工作的顺序

### 1. 先确认实际运行对象，保护本地工作

读取仓库 `git status --short`、当前提交与相关差异；发现未提交改动先逐项保留和审查，使用独立副本开展验证。不要执行 `reset --hard`、强制检出、无审查覆盖、自动合并或自动发布。

读取故障机实际 `dlc_load.json`，逐个解析启用 `.mod` 指针的 `path` 与名称，再读取这些实际目录中的 `descriptor.mod`。区分本地模组与创意工坊副本、重复启用和失效指针；确认游戏版本、加载顺序、0.7.4 源文件及工具是否为本次版本。界面版本号或仓库中存在文件都不能证明游戏加载了它。

对故障机全部启用模组检查：同名预算 scripted effect、5 个事件的定义与覆盖优先级、5 个国库契约、发展法案组、预算窗口、`replace_path`，以及额外 `enact_treasury_budgets*`/`set_treasury_budget_base_rate*` 调用。冲突要对照实际加载顺序处理，不要仅把 TEQ 放最后就宣称兼容完成。

可先运行下列检查；游戏目录按故障机实际位置填写，须指向含 `common`、`events` 的 `game` 目录：

```powershell
$gameDir = '<故障机实际 CK3 game 目录>'
node tools/validate-treasury.js --game "$gameDir"
node tools/test-treasury-finance.js
```

### 2. 锁定具体中央与具体封臣

先记录故障发生日期、中央和至少一位异常文官/军事封臣的角色 ID、主要头衔、政体、直属领主与最高领主。区分“没有预算行”“实际支付为零”“金额偏低”“打开面板后才恢复”，并与一位正常的同类封臣比较。

优先在打开预算面板、调整比例或手动执行预算之前留取状态，因为打开面板本身会校准，可能抹去故障现场。结合界面、可安全读取的副本存档和新会话日志核对以下数据：

| 对象 | 重点观察 |
|---|---|
| 中央 | 原生当月收入/结余、`character_treasury_new_budget_capacity`、原生已执行容量、各通道份额/基准/实际接收人，主要头衔上的 `teq_total_budget`、`teq_available_flow`、`teq_public_budget`、`teq_payroll_total`、`teq_native_*_units`、政策版本及玩家比例设置 |
| 地方 | 是否满足有地伯爵及以上、国库/预算接口和直属领主资格；文官/军事契约标志；地方国库与储备目标、`teq_region_owner`、`teq_region_weight`，中央名单是否包含其当前主要头衔 |
| 地方角色 | `teq_flow_title` 是否等于当前主要头衔、`teq_fiscal_owner` 是否指向正确中央，以及 `teq_public_tax`、`teq_refund_paused`、发展/财富修正或军事修正是否完整且角色分类正确 |

军事金额须核实原生职责/契约与接收人，不能仅凭“有军事份额”推断每个封臣都应收军费。男爵、无地人物、非国库直属领主下的地方、无可用资金或有意设为 0% 的通道，应与代码缺陷分开记录；是否扩大适用范围需询问用户。

### 3. 在副本中进行引擎推进验证

关闭游戏后备份原模组与故障存档，保留原始证据；只在测试副本安装或合并修复版，重启游戏确认实际加载。不要直接在唯一铁人存档上试验，也不要覆盖故障机尚未提交的修改。

先对同一副本记录加载后、首次迁移前后及首次打开预算面板前后的状态，再至少跨过两至三个结算月，逐月比较中央支出与异常封臣实收。记录每一步的游戏日期与触发动作，避免把 UI 即时重算误记为月度付款。

在独立副本分别验证：新封臣加入、主要头衔继承、中央失去统筹资格/地方转封、文官与军事职责切换、收入或军费变化、原生预算政令及年度备用预算重算。确认政策缓存更新为 14，同时原有玩家比例和工资微调保留；每个场景核对接收人、修正与支付，不仅检查日志无报错。

若仍复现，提交最小可解释的“日期—中央—具体封臣—操作—原生值—TEQ 值—实际收支”对照。优先判断资格/归属错误、原生接收人缺失、实际加载冲突、缓存时序或公式问题，再作最小修复。无法从设计和证据确定的玩法改动先问用户，不要继续叠加硬编码限制。

### 4. 交付前留下可复查结果

报告故障机实际版本与加载来源、能否复现、覆盖的具体场景、源码验证和引擎推进结果，以及未验证部分。修改代码时补与真实触发条件对应的回归，并提供清晰差异；**不要自动合并远端分支、覆盖他人改动或把尚未实测的结果表述为已验证。**
